## 三、资源模型 ✅ 已统一

**"投入经验" ≡ "投入魔法点数"。** 全链路：

```
原版等级 / 经验  ──┐
                  ├──→ 魔力值上限 ──→ 魔法点数 ──→ 解锁魔法
亲和力总和 ───────┘         │
                            └──→ 魔力值（施法消耗，随时间恢复）
```

| 量 | 来源 | 用途 |
|---|---|---|
| **魔力值上限** | 初始值 = f(亲和力总和) + 原版等级成长 | 决定魔法点数档位 |
| **魔力值** | 上限之内，**随时间恢复** | 施法消耗 |
| **魔法点数** | 按魔力值上限的档位给 | **解锁魔法**（= 投经验）|

## 十、施法方式

**右手持法杖** + **长按不同数字键** → 释放对应魔法。

### 10.1 实现路线（2026-09-15 查证后确定）

先摆一个**硬约束的修正版**：SpellEngine 原版 jar 是 Fabric/intermediary 名字，Forge 侧编译不了 ——
**但整合包 `mods\.connector\` 里有 Sinytra Connector 重映射过的版本**
（`spell_engine-..._mapped_srg_1.20.1.jar`），签名是正常 MC 类名，**我们的 Forge mod 可以直接调**。
（拷进 `D:\ModTest\libs\`，build.gradle 里 `compileOnly`；没引擎的环境靠
`ModList.get().isLoaded("spell_engine")` + 内层类隔离来保护。）

分三步走：

| 步骤 | 做法 | 状态 |
|---|---|---|
| **A** | 法术进 **spell pool**（纯数据）→ 玩家拿法术书走引擎原有流程，数字键施放 | ✅ 2026-09-15 已把 tnc 5 个雷法并进 `ysjx_weapons:lightning` 池 |
| **B** | 魔法石 GUI 成为唯一入口：解锁成功 → **Java 用引擎 API 直接把法术写进玩家法术书**（`SpellContainerHelper`）| ✅ 2026-09-15 已实现（`magic\compat\SpellEngineBridge`）|
| **C** | 自研法杖 + 自研施法：魔力/冷却/已学**在施法前**判定 | ⚠️ 不必做了 —— 见 10.2，用 Mixin 拦 `attemptCasting` 已经实现了"施法前判定" |

**关于魔力值**：`CombatEvents.SPELL_CAST`（引擎公开的施法事件）是**观察者事件、不可取消**，
所以它本身只能做"**事后扣**"：`RELEASE` 时扣魔力，不足则魔力清零 + 力竭惩罚，`CHANNEL` 时提前警告
（`magic\compat\SpellEngineManaHook`）。
**但"拦不住"这个限制已经被 10.2 的 Mixin 解决了** —— 硬拦截生效时魔力不够的法术根本进不到 `RELEASE`，
上面那条"勉强施法"分支正常情况下永远走不到，只作为 **Mixin 静默失效时的兜底**保留。
包里 `config/spell_engine/client.json5` 已经把**数字键 1–9 施法**配好了，所以不需要我们劫持按键。

### 10.2 魔力硬拦截（"没魔力放不出来"）—— ✅ 已实现（2026-09-15）

引擎没给可取消的施法前钩子，但 `SpellHelper.attemptCasting(Player, ItemStack, ResourceLocation)`
就是它自己的施法前判定，返回 `SpellCast$Attempt`（有 `success()` / `failMissingItem()` /
`failOnCooldown()` / `none()` 工厂）。所以我们：

> **Mixin `net.spell_engine.internals.SpellHelper.attemptCasting`（4 参那个重载）**：
> 是我们的法术 + 服务端 + 魔力不足 → 返回 `Attempt.none()` → **引擎自己拒绝施法**。

**只注入一个重载，不是两个**（用 `javap -c` 对着真引擎核过）：

```
attemptCasting(Player, ItemStack, ResourceLocation)           // 3 参：纯转发
    iconst_1
    invokestatic attemptCasting(...,Z)                        //   → 转调 4 参
attemptCasting(Player, ItemStack, ResourceLocation, boolean)  // 4 参：真正的实现
    checkcast SpellCasterEntity / SpellRegistry.getSpell(id)
    isCoolingDown(id) / ammoForSpell(...) / Attempt.success()
```

**所有调用路径最终都汇聚到 4 参那个方法**，所以只在一个点注入就够。
而且 `required:false` + `defaultRequire:1` 下**任何注入点没对上都会让整份配置静默失效**
（游戏照常启动，只是再也拦不住施法）—— 每个注入点都是一条"静默失效"路径，越少越安全。

- `remap = false`（目标类/方法是引擎自己的名字，不受 Connector 重映射影响，不需要 refmap）
- 纯逻辑在 `ManaGate`（可判、可自检），Mixin 只是薄适配器
- `/tnc engine` 查「引擎已加载 / Mixin 加载没加载」；**`/tnc gatetest` 直接实测拦不拦得住**

**⚠️ 踩过的坑（`TncMixinPlugin`，已删除）**：曾经用一个 Mixin 插件类做"没装引擎就不注入"，
插件里调 `ModList.get().isLoaded(...)` —— 但 Mixin 配置 prepare 阶段 `ModList` **还是 null**，
于是 NPE → `InvalidMixinException` → `[net.minecraft.server.Main/FATAL]: Failed to start the minecraft server`。
**dev 环境不复现，只在实际整合包里炸**。现在改用 `required:false`，插件彻底删掉。

备选方案（自研施法入口：调 `startCasting` / `performSpell` / `imposeCooldown`）暂时不需要了，
留作以后要完全自主时的退路。

### 10.3 实测硬拦截：`/tnc gatetest`

静态验证（字节码描述符比对）只能证明"注入器**应该**对得上"，证明不了"运行时**真的**注入了"。
而上面那种静默失效必须能当场看见，所以做了一条命令，在**一次性假玩家**上跑三级阶梯：

| 步骤 | 条件 | 期望 |
|---|---|---|
| 1 | 魔力**够**、但**没解锁** | 拦住，算在"未解锁"头上 |
| 2 | 已解锁、魔力**差 1 点** | 拦住，算在"魔力不足"头上 |
| 3 | 已解锁、魔力**刚好够** | **放行** |

第 1 步同时承担"注入到底生效没有"的举证责任：它看 `ManaGate.gateChecks` 涨没涨，
而那个计数器是**注入进去的代码里加的** —— 涨了就说明注入真的生效，这是伪造不了的证据。
三步合起来才说明"判定在按魔力和解锁状态区分"（一个永远返回"拦"的实现也能过第 1 步）。

不碰真玩家任何数据（全在假玩家上跑）；引擎不在时明确报"跳过"，不算失败。

**验证状态**：注入本身已经在 dev 用**桩引擎**证明过了 —— Mixin 日志出现
`Mixing SpellHelperManaGateMixin ... into net.spell_engine.internals.SpellHelper`，
且三级阶梯 `4/4 passed`（gateChecks +1 / 未解锁=拦 / 差 1 点魔力=拦 / 刚好够=放行）。
详见 `PROJECT-STATE.md` §4.15.4。**只剩"Connector 环境下能不能注入"要整合包实测。**

## 十七、已实现：魔法石 GUI 第一版（2026-09-15）

阶段 3 的第一版：**能看数据、能花点数解锁法术**。取代卷轴的那一步就从这里开始。

### 17.1 入口：物品栏中间那颗石头（**不需要 Mixin**）

设计文档原本写的是「Mixin `InventoryScreen`」，实际实现改用了
Forge 自带的界面事件：

```java
@Mod.EventBusSubscriber(modid = TNMod.MODID, value = Dist.CLIENT, bus = Mod.EventBusSubscriber.Bus.FORGE)
public class MagicStoneClientEvents {
    @SubscribeEvent
    public static void onScreenInit(ScreenEvent.Init.Post event) {
        if (event.getScreen() instanceof InventoryScreen inventory) {
            event.addListener(new MagicStoneButton(inventory.getGuiLeft() + 81, inventory.getGuiTop() + 44));
        }
    }
}
```

好处：不用配 mixin/refmap，也不会和包里那一堆界面 mod（FancyMenu / ModernUI / HUD）抢屏幕。
石头位置在**玩家模型和右上角合成栏之间的空档**（`+81, +44`）。

`MagicStoneButton` 继承 `AbstractWidget`，用 `GuiGraphics.fill()` 画了个三层菱形宝石
（悬停会变亮）。**这不是最终美术**，以后换成贴图或模型。

### 17.3 解锁流程（服务端权威，四条门槛）

`MagicStoneLearning.check()` —— **命令和 GUI 共用同一份判定**，所以两边结果永远一致：

| 顺序 | 门槛 | 不满足时的提示 |
|---|---|---|
| 1 | 没学过 | 已经学过了 |
| 2 | 等级 ≤ 亲和力允许的上限 | 亲和力不足 |
| 3 | **不能跳级**（必须先学上一级） | 需先学上一级 |
| 4 | 可用点数 ≥ 该等级花费 | 魔法点数不够 |

解锁成功：扣点数 → 记进 `learned` → 把该元素进度推到这一级（**不可撤回**，以后靠遗忘药水）。

### 17.4 网络包（两个方向各一个）

| 包 | 方向 | 作用 |
|---|---|---|
| `SyncMagicStone` | 服务端 → 客户端 | 整包同步数据（登录、改数据、命令、解锁后都发） |
| `MagicStoneActionPacket` | 客户端 → 服务端 | `REQUEST_SYNC`（打开界面拉数据）/ `UNLOCK`（解锁某法术） |

⚠️ 踩过一个坑：界面 `init()` 里请求同步 → 服务端回包 → 界面刷新（`rebuildWidgets` → 又 `init`）
→ 又请求同步 …… **死循环**。现在用 `syncRequested` 标志位保证只请求一次。
