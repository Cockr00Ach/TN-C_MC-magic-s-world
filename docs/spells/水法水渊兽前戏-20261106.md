# 水法唤兽门 · 真实水渊兽残影（2026-11-06 第二版）

作者原话：**「水法的前戏你也可以优化做做，我希望是周围随机出现一个不同角度的小法阵，
然后跑出我们的小型蓝金水渊兽的身影飞进玩家的身体，脚边出现小水波」**。

第一版把整张潮汐封印缩成侧门，又用 `miniBeast` 手画了七段蛇形残影；作者纠正：
**「法阵这么丑？？？然后我说的小兽是我们的水系boss的模型，你把他缩小了不就行了？
加上透明度即可啊」**，并补充**「我刚刚说的法阵是唤出小兽的法阵」**。

第一版装进实际客户端后，作者反馈：**「我没看见小兽啊，啥都没有啊，你学习一下雷法暗法
他们怎么做的，然后前戏内容你自己再丰富优化一下」**。因此本轮不是加一点粒子，而是
**换实现路线 + 重做读条空间**：

1. 不再依赖实体 renderer 的 `reRender/actuallyRender`，改成和
   `LightningCastFx` / `DarkCastFx` 一样的**即时 `MultiBufferSource` 提交**；
2. 主门固定放在玩家**正前方 ±60°**，第一人称一抬头就能看见，不再 360° 随机到背后；
3. 主门之外再加一张更小的**回声门**，门里加八片张开的潮叶、地面水线、拖尾和兜底水影；
4. 残影仍使用**水系 Boss 自己的 GeckoLib 模型、原骨骼、原 1024×1024 贴图**，
   只缩小 + 半透明，不另建实体、不发包、不改 Boss。

> 本文只描述玩家水法读条里的唤兽门。脚下主阵、Boss 阵、`WaterSpellRules` 的伤害/半径/
> 读条时长都没有改。

## 一、每个读条只随机一次，而且偏向正前方

`WaterCastFx.CastState` 在构造时取一次随机值，整段读条固定：

| 字段 | 含义 |
|---|---|
| `playerCast` | 只有玩家读条才走唤兽门 + 残影；Boss 为 false |
| `sideAngle` | 主门方位：以玩家视线 yaw 为 0°，再加 `±60°` 内随机 |
| `sideDistance` | 主门距玩家中心 `2.05..2.90` 格 |
| `sideHeight` | 立/斜门基准中心高度 `0.95..1.60` 格 |
| `sideStyle` | 本轮只取 `1` 立着朝玩家 / `2` 斜插，不再用平贴地面（平门第一人称最容易看不见） |
| `echoAngle` | 回声门方位：主门再偏 `±106..137°` |
| `echoDistance` / `echoHeight` / `echoStyle` | 回声门 `2.25..3.40` 格、`0.78..1.48` 格，平/立/斜三种 |
| `beastStart` / `beastEnd` | 残影出场/入体的读条比例，约 `0.13..0.18` 和 `+0.55..0.67` |
| `beastImpacted` | 入体水花只触发一次 |

“正前方”是按**开始读条时的玩家 yaw**算的；读条过程中转身，门不会跟着转（否则会像
贴脸 UI）。这是有意的固定空间锚点。

## 二、唤兽门：一扇主门 + 一张回声门

### 主门

- **位置**：`sideCenter`；立门中心高度 `max(sideHeight, gate+0.18)`，斜门
  `max(sideHeight, gate+0.22)×0.72`，保证圆环下缘不切地。
- **朝向**：立门法线水平指向玩家；斜门法线约
  `(-cosθ×0.62, 0.78, -sinθ×0.62)`，向玩家倾斜约 39°。
- **大小**：`gate = 0.74 + tier×0.05` 格；t1 约 0.79，t5 约 0.99。
- **画法**（`WaterCastFx.gateFx`）：
  - 一层 `alpha×0.18` 深蓝水镜，先压住门后的草地/石头；
  - 外环 `gate` 宽 `0.022`，外圈 `1.08×gate` 的极细青白晕，主门再加 `1.18×gate` 的淡晕；
  - **八片水叶**：从 `0.22×gate` 内圈斜张到 `0.90×gate` 外圈，随 `time` 慢转，读作“门在开”；
  - 四段留白潮弧在 `0.76×gate`，每段约 50°；
  - 四枚 `0.84–0.95×gate` 短金刻度；
  - 中心 `0.22×gate` 细环 + 露珠 + 随读条变亮的门心；
  - 三颗 `1.15×gate` 绕门水珠；
  - 兽出场瞬间（`p≈0.13`）门心向外爆一圈短亮环；
  - 门心到地面一圈 `0.60×gate` 地面水波 + 三条细水线，门不再悬空。
- **出现/消失**：`p≈0.03` 淡入，`beastEnd+0.06` 后淡出；残影飞走后门自然关闭。

### 回声门

- 半径 `.46 + tier×.03`，透明度约主门的 1/3；**只做“周围还有门”的空间层次，不放第二只兽**。
- 出现比主门晚 `0.10` 个读条比例，消失比主门晚 `0.04`，让主门先关、回声门最后收。
- 位置可能落在玩家侧后方，这是有意的：主门保证“看见”，回声门负责“周围一圈都有仪式感”。

## 三、真实 Boss 模型残影

实现：`client/LeviathanGhostVisual.java`。

- **模型/贴图**：`TNWaterLeviathanEntity.modelResource()` +
  `textures/entity/water_leviathan_bedrock.png`，通过实际 Boss 渲染器的
  `GeoRenderer.getGeoModel().getBakedModel(...)` 烘焙；不复制几何。
- **缩放**：`GHOST_SCALE = 0.12`，再乘路径 `0.64..1.0` 和淡出缩小。
  原模型跨度约 17 格，残影约 **1.3–2.1 格长、0.8–1.3 格宽**。
- **透明度**：`RenderType.entityTranslucent(texture)`，顶点 alpha 为
  `(0.68 + 0.18×chargeGlow) × fadeIn × fadeOut`；`u<0.12` 淡入，`u>0.84` 淡出并缩小。
- **为什么这次能看见**：
  - 不调用 `EntityRenderer.render` / `GeoRenderer.reRender`，避开 Boss 的
    `withScale(4)` 和不透明发光层；
  - 也不再调用 `actuallyRender`：它只遍历骨骼，**不套实体朝向**，第一版很可能因此
    侧着/背对镜头；
  - 现在自己压 `scale` 和 `Axis.YP.rotationDegrees(180 - yaw)`，再对每个
    `model.topLevelBones()` 调 `renderRecursively(..., isReRender=true, ...)`；
  - `LightTexture.FULL_BRIGHT` + `OverlayTexture.NO_OVERLAY`，深水/夜间也看得见蓝金轮廓；
  - `isReRender=true` 跳过 Boss 发光层，只画原贴图这一层；
  - 残影不是实体，不进入世界、不参与碰撞、不发送网络包。
- **兜底**：如果 renderer 不是 `GeoRenderer`、模型烘焙失败或 `render` 返回 false，
  同一帧改画 `ghostWisp`（一颗亮水珠 + 一圈小环 + 三根短水线），并写一条
  `TN-C/waterghost` 日志说明原因；不会再出现“整段前戏什么都没有”。
- **回声残影**：主残影后方 `u-0.055` 再画一只 alpha×0.26 的淡影，让飞行有拖尾。
- **节奏**：起点在门心沿法线外 `0.22` 格，终点 `(0, 1.12+tier×0.035, 0)`；
  控制点在两点中点上方 `0.78+0.08×tier`，再沿切向偏 `0.24`（立门 `0.42`）。
  到 `beastEnd` 触发 `absorb(...)`：胸口向内收的水花 + 脚边一圈小水波粒子。

## 四、脚边小水波与读条粒子

- 几何：`WaterWaveVisuals.rippleGlow`，半径 `min(2.6, 1.05+tier×0.12)`；
  两圈很淡的水环，始终存在。
- 粒子：每 tick 脚边撒 1–2 颗 `SPLASH`（`MINIMAL` 下 1 颗）；残影飞行时沿路径
  补 `FALLING_WATER`/`BUBBLE`；主门出现后、兽出场前，门心往下滴 `FALLING_WATER`，
  偶尔冒 `BUBBLE`；入体时胸口和脚边各一圈吸收水花，并给一层很短的屏幕水膜。
- 没有重新引入旧版“屏幕高的潮墙”。

## 五、边界与预算

- **不穿地**：立门/斜门圆心高度必须大于圆在竖直方向的投影半径；测试对 t1–t5
  各随机 250 次，断言 `center.y - verticalExtent > 0.01`。
- **不穿玩家**：门心到玩家水平距离减半径 `> 0.35` 格，同样随机 1250 次。
- **主门在正前方**：以 `lookYaw` 为 0° 的 ±60° 扇区内随机 250 次，断言 `z>0` 全部成立。
- **模型预算**：残影复用 Boss 模型（271 个 cube），只画一次本体 + 一次很淡的回声；
  不新建实体、不常驻内存网格。
- **不穿墙**：门仍可能生成在树干/墙体内部；本轮没有做视线检测，这是已知边界。
- **光影**：实际整合包有 Oculus/Embeddium/ModernFix，`entityTranslucent` 仍可能被
  光影替换；兜底只在 `render` 返回 false 时触发，不能感知“提交了但被 shader 画没”。
  如果仍看不见，下一步应改成与雷法/暗法完全相同的自定义加色层剪影，而不是再调 alpha。

### 打通整包编译的两处队友水法合并

04:54 构建时队友水法正在改，`TNWaterSpellEntity` 里有两个同签名
`remove(RemovalReason)`，`DragonRoarCombo` 又把 `LivingEntity caster` 传给只收
`ServerPlayer` 的 `TNWaterFieldEntity.aimEnemy`。为了不卡住整包，做了最小合并：

- `TNWaterSpellEntity.remove` 保留一份：先 `WaterRestraints.release`，再 `prison.discard()`，
  最后 `super.remove(reason)`；两段逻辑都保留。
- `TNWaterFieldEntity.aimEnemy` 参数从 `ServerPlayer` 放宽为 `LivingEntity`，方法体只使用
  `getEyePosition/getLookAngle/level/clip` 和 `WaterSpellRules.enemy`，对玩家和 Boss 都成立。

## 七、未实机验证（重要）

本轮**没有完成客户端画面验收**：尝试用隔离开发客户端跑一个只画残影的 audit 场景，
但开发端被队友的 `ArcanaWaterWalkMixin` refmap 目标缺失挡在启动阶段，随后放弃该临时
audit（已删除，不进最终 JAR）。因此以下仍必须在实际整合包里看：

- 残影是否真的出现、是否朝向飞行方向，而不是侧着/倒着；
- 0.2–0.4 秒短读条里，1.3–2.1 格长的 Boss 模型是否太大、太糊或穿进玩家；
- 半透明残影与主门、回声门、脚边水波、SpellEngine 释放粒子是否互相抢眼；
- 主门在正前方是否真的第一眼可见；斜门是否仍会被地形挡住；
- 如果模型太透明/太亮，优先调 `LeviathanGhostVisual.GHOST_SCALE` 和
  `ghostFor(...)` 里的 alpha；不要动 Boss 本体或 `WaterSpellRules` 的数值。

如果实际客户端里仍然完全看不到兽，先看 `logs/latest.log` 有没有
`TN-C/waterghost` 的 `direct GeckoLib render armed` / `ghost render disabled once`
日志：前者说明模型路径已走通（问题在 shader/透明度），后者会直接给出原因。
