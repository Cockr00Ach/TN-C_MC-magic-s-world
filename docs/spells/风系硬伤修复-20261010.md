## 二、改动 1：风速链 5 个法术**全程静音**

**真因**：五个法术的 `cast.sound.id` = `spell_engine:generic_wind_casting`、`release.sound.id` = `spell_engine:generic_wind_release`，
而引擎 `assets/spell_engine/sounds.json` 注册的 **18 个事件里只有 `generic_wind_charging`** —— **根本没有 wind 的 casting / release 这一对** ✗。
音效 id 解析不到 = **静默**（日志里连一条错误都没有 ✗）。

**改法**（改生成器 `tools/gen_tnc_wind_spells.ps1`，不手改产物 ✓）：

```
-  "sound": { "id": "spell_engine:generic_wind_casting", "randomness": 0 },
+  "sound": { "id": "spell_engine:generic_wind_charging", "randomness": 0 },
-  "sound": { "id": "spell_engine:generic_wind_release" }
+  "sound": { "id": "spell_engine:generic_wind_charging" }
```

**为什么用 `generic_wind_charging` 而不是自己加音效**：
- ✅ 整合包里**所有别的风系法术都用它** —— 作者自己的 `wind_gust` / `wind_tornado`，以及我们的 gale 链 ✓（一致性最好）
- ✗ **不能**去改第三方 mod 的 jar（铁律 ④：Fabric 侧重映射会崩）
- 🟡 想真做出 casting/release 就得我们自己的 `assets/tnc/sounds.json` + 两个 `.ogg` —— **需要风声素材，本次不做**

**验证**：重新生成后 `git diff` **只有这 10 行**（两行 × 5 文件）⇒ 生成器其余部分与发货文件本来就一致 ✓。

## 三、改动 2：风球链 **t4 严格劣于 t3**、**t5 等于 t3**

**真因**（三条一起）：t3 / t4 / t5 **共用同一个标记** `tnc:wind_spirit`，而 `TNWindMechanics.orbCount()`
对那个标记**一律返回 5** ⇒ 三档在实装里**是同一个东西** ✗：

| 档 | 法术 | 改前 | 问题 |
|---|---|---|---|
| t3 | `wind_spirit` 召唤风灵 | `wind_spirit` **30s** / cd 25 | — |
| t4 | `triple_wind_spirit` 召唤三个风灵 | `wind_spirit` **15s** / cd 35 | **每个维度都比 t3 差**（效果同、时长短一半、冷却更长）✗ 名字里的"三个"在实装里**没有对应物** ✗ |
| t5 | `wind_spirit_lord` 风灵之主 | `wind_spirit` 30s / cd 60 | **与 t3 逐字相同** ✗（`SpellCatalog` 注释自己写着"5 用户还没定，先占位"）|

**改法**（一档一行，谁都能看懂）：
1. `tools/gen_tnc_wind_summon_spells.ps1`：t4 → `wind_spirit_ii` **40s**、t5 → `wind_spirit_lord` **45s**；
2. `TNWindMechanics`：新增两个标记 `WIND_SPIRIT_II` / `WIND_SPIRIT_LORD`，并把散在 if 里的档位换成**一张显式的表**：

| 档 | 法术 | 标记 | 球 | 伤害倍率 | 单次伤害 |
|---|---|---|---|---|---|
| t1 | 召唤风球 | `wind_orb_three` | 3 | ×1 | 4 |
| t2 | 召唤五个风球 | `wind_orb_five` | 5 | ×1 | 4 |
| t3 | 召唤风灵 | `wind_spirit` | 5 | ×2 | 8 |
| t4 | 召唤三个风灵 | `wind_spirit_ii` | 5 | ×3 | 12 |
| t5 | 风灵之主 | `wind_spirit_lord` | 5 | ×4 | 16 |

⇒ **球数、倍率、时长三轴全部单调递增** ✓，t4 不再是倒挂、t5 不再是复制 ✓。
3. `tools/verify_mod_jar.ps1` 的效果白名单补上两个新 id（`tnc:wind_spirit_ii` / `tnc:wind_spirit_lord`），
   否则闸门会判"引用了未注册效果" ⇒ **装机被挡** ✓。

**判定顺序是从最高档往下认**（有意的）：法术各自用 `apply_mode: SET` 设自己的标记，
低级那次可能还没到期 ⇒ 只判"有没有某个标记"会认错档 ✗。

> ⚠️ **诚实说明**：这是**把阶梯修直**（消除倒挂），**不是**提案里的新设计 ✗。
> 「召唤三个风灵」的字面意思（真的三只）**仍然表达不出来** —— 那要等实体化（提案 §5.2）✓。
> t4 的 15s 原本来自用户规格（"三个风灵各存在 15s"），但那条规格是**按另一种机制**写的；
> 在共用标记的实现下它只造成了"4 级更弱"，所以本次改成 40s ✓。

## 五、★ 发现 2：闸门有一处**覆盖缺口**（本次没动，等你定）

`tools/verify_mod_jar.ps1` 里那张法术清单 `$spellIds` **只到"风系链 1"**，原文写着：

```
# wind chain 1 (the other 10 wind spells get added when their json exists)
'tnc:wind_field', 'tnc:wind_speed', 'tnc:greater_wind_speed',
'tnc:super_wind_speed', 'tnc:wind_god_descent',
```

**而那 10 个法术的 JSON 现在都在**（风球链在 kubejs、范围风链在 jar）⇒ 这句话**已经过期** ✗。

**后果**：`$spellIds` 驱动**好几项检查**（图标在不在、`effect_id` 注册没注册、`SPAWN` 的实体注册没注册、
`SELF/CURSOR + area_impact` 硬规则），所以**这 10 个法术从来没被闸门查过** ✗ ——
换句话说，我这次改的静音 / 档位 / 图标，**闸门本来就拦不住**（这也解释了为什么"10 张图标缺失"能一直绿灯 ✗）。

**为什么我没有顺手补上**：`$spellIds` 还被用来要求 **`data/tnc/spell_assignments/magic_wand.json` 必须列全** ✓。
我核过：那份文件列了 **58 个 tnc 法术**，风系只有那 5 个，**这 10 个不在里面** ✗。
⇒ 把 10 个 id 加进 `$spellIds`，**闸门会立刻红**，然后就必须同时改 `magic_wand.json`（那是**法杖池**的定义，
属另一个子系统，还有 `SpellCatalogStructureTest` / `SpellLoadoutTest` 在管）✗ —— 这一步**需要你拍板**，不适合塞进"无争议修复" ✓。

**顺带一个待确认的问题**（我没能在游戏里验 ✗）：**这 10 个法术现在能不能从法杖放出来？**
- 支持"能"的证据：`SpellEngineBridge.orderedSpellIds()` 是**运行时按 `SpellCatalog` ＋ 已解锁 ＋ 引擎注册表**算出槽位的，
  写容器时用的是 **`is_proxy = false`**（源码注释："容器的 spell_ids 就是权威（快捷栏直接读它）"）⇒
  **快捷栏读的是运行时算出来的那份，不是 `magic_wand.json` 里那张静态表** ✓
- ⇒ 若如此，那 10 个法术**本来就能放**，`magic_wand.json` 那张表只是"一致性/历史"用途 ✓
- ⚠️ **但我没有在游戏里实测过** ✗ —— 请实机试一次「学一个风球 / 范围风 → 法杖有没有对应槽位」，
  把结果告诉我，就知道要不要动那张表 ✓
