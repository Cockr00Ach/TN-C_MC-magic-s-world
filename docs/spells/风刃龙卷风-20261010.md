## 三、两个新实体 ＋ 一个施法钩子

### 3.1 `TNTornadoEntity`（`tnc:wind_tornado`）

**"一直在旋转"** ＝ 渲染器每帧按实体的 `spin()` **绕 Y 转模型** ✓（模型本身是静态的 ✓，
不做动画 —— 转起来就够，而且省一套动画文件 ✓）。

- **位置固定**在召唤点（不追人 ✓），有**寿命**（t3 8s / t4 12s / t5 16s）；
- **持续向外吐风刃** ✓：每 `FIRE_INTERVAL` tick 朝**均匀分布的方向**各吐一发
  （`BURST` 发/轮，t3 3 发、t4 4 发、t5 6 发 ⇒ "风神之刃"真的像风暴 ✓）；
- 顺带对**贴近的**敌人有**吸力**（`suckIn`）＋ 每轮一次小额伤害 ⇒ 有"卷进去"的读感 ✓；
- 到寿命/主人没了就 `discard` ✓。

### 3.2 `TNWindBladeEntity`（`tnc:wind_blade`）

龙卷风吐出来的**风刃**：走**直线**（不受重力 ✓）、命中第一个目标就结算伤害 ＋ 牵引，
飞够距离或超时就消失 ✓。**渲染复用第三批那个月牙模型** ✓（`projectile/windblade`）
—— 所以"风刃"的造型还是作者要的那个月牙 ✓，只是现在由龙卷风来吐。

### 3.3 `TNWindGaleMechanics`（施法钩子）

接**引擎自己的** `CombatEvents.SPELL_CAST`（不是 Forge 总线 ✗），
按 `group == "gale"` ＋ `learn.tier` 判档：

- `tier < 3` ⇒ **直接返回** ✓（t1/t2 照旧走引擎投射物，Java 不插手 ✓）；
- `tier >= 3` ⇒ 在**施法者身前**召唤龙卷风 ✓。

⚠️ **`ensureLoaded()` 必须挂上** ✗（已加进 `TNEffects.register`）—— 和黑夜之手同一个坑：
不在"任何施法之前"把类加载起来，**第一次放 t3 只会扣蓝、不出龙卷风** ✗。

**落地点的处理**：先按视线方向取身前 6 格，再**从该点向下找最多 4 格**的地面 ✓
—— 直接放在眼睛高度会让龙卷风**浮在空中** ✗（模型底边是贴地的 ✓）；
找不到地面（悬崖边）就用原高度 ✓，宁可浮一点也不掉进虚空 ✓。

## 七、★ 紫黑事件复盘：模型**根本没被烘焙**（装机后才暴露）

作者实机反馈：「**龙卷风模型是紫黑啊**」✗。**两个 bug，都在生成器里**，
而且**闸门当时一个都没拦住** ✗ —— 这段是本次最值钱的记录。

### 7.1 主因：`texture_size` ⇒ 模型永远不被烘焙

生成器吐了：

```json
{ "credit": "...", "texture_size": [32, 32], "textures": {...}, "elements": [...] }
```

**原版模型规范不认 `texture_size` 这个字段** ⇒ 整个模型**烘焙失败** ⇒
引擎的 `CustomModels.render` 拿不到烘焙结果，退回 Forge 的 **missing model**
⇒ 屏幕上就是那个**紫黑格子立方体** ✓。

- **配方文档早就写着这一条** ✗：`docs/spells/投射物模型_配方.md` §「Blockbench 导出后
  必须手改的两处」明确列了 `texture_size`，并注明**"直接放进 jar 就是不能被烘焙"** ✓；
  而且 `tools/import_author_model.ps1` **专门会把它删掉** ✓ ——
  **手写导入那条路有防护，我们自己的生成器反而没有** ✗。
- **为什么月牙/风灵没事**：`gen_wind_blade_model.py` 和 `gen_wind_sprite_model.py`
  **都没写这个字段** ✓（事后审计：全仓生成的模型里**只有** `wind_tornado.json` 带它 ✗）。
- **教训**：那份配方文档的"禁止字段"清单，**生成器也必须遵守** ✓ ——
  它是"手改导出的坑"，但对生成器同样致命 ✓。

### 7.2 次因：`"uv": [0, 0]` 是个**退化的 UV**

同一份模型里每个面的 UV 写成了 **2 个值**：

```json
"faces": { "north": { "uv": [0, 0], "texture": "#0" }, ... }
```

面 UV 必须是**四值矩形** `[u1, v1, u2, v2]` ✓ —— 两值会被当成退化矩形，
**整个面塌到一个像素上** ✗。对照同仓能正常显示的模型：
`windblade` 是 `[0.0, 0.0, 1.0, 16.0]`、`dark_hand` 是 `[14, 12, 20, 18]` ✓，**都是四值** ✓。
（这个 bug 就算烘焙成功也只会"糊成一片色"，是**第二个**独立问题 ✓。）

**顺带纠一个我自己的错**：我第一版把 UV 写成像素坐标，改的时候才发现
**面 UV 用的是原版 0..16 空间、不是像素** ✗ ⇒ 画贴图时必须乘 `(贴图尺寸 / 16)` ✓
（32×32 图 ⇒ ×2）。写进生成器注释了 ✓。

### 7.3 补的闸门（让这类 bug 不能再悄悄发货）

`tools/verify_mod_jar.ps1` 新增 **D1b10**：扫 `assets/tnc/models/projectile/*.json`，

1. **出现 `texture_size` ⇒ 直接 FAIL** ✓（附一句"vanilla spec rejects the model =>
   it is never baked => purple-black in game"）；
2. **任何面的 UV 不是 4 值 ⇒ 直接 FAIL** ✓。

**负向测试做过** ✓：把 `texture_size` 注回去跑闸门，确实报
`[PROBLEM] projectile model(s) that will NOT bake (purple-black in game)...` ✓，
删掉后恢复 `[ok] every projectile model is bakeable` ✓。

> ⚠️ **为什么原来的闸门没拦住**：已有检查覆盖的是"**模型在不在烘焙列表里**"
> （`PROJECTILE_MODELS` / 文件存在 / 贴图存在 / 尺寸在 −16..32），
> 全是**"文件层面"**的检查 ✓ —— 而 `texture_size` 让**文件全都在、内容也合法**，
> 只是**烘焙器不认** ✗。**"文件在" ≠ "能烘焙"** ✓，这是原来检查的盲区 ✓。

### 7.4 状态

已按 `tools/gen_wind_tornado_model.py` 重新生成 ＋ 装机 ✓；实例 jar 里解包核对：
**模型没有 `texture_size`、UV 全是 4 值** ✓。提交 `56fb0045` ✓。

## 八、★ ★ 真正的原因（作者第二次报「紫黑」后，实机日志实锤）

作者复测后反馈：**风刃正常、龙卷风还是紫黑** ✗。查**实机 `logs/latest.log`**（那是唯一能定案的地方）：

```
[Worker-ResourceReload-3/ERROR] [ModelManager]: Failed to load model tnc:models/projectile/wind_tornado.json
com.google.gson.JsonParseException: Invalid rotation 67.5 found, only -45/-22.5/0/22.5/45 allowed
    at net.minecraft.client.renderer.block.model.BlockElement$Deserializer.deserialize(BlockElement.java:112)
[Worker-ResourceReload-2/WARN] [ModelBakery]: Unable to load model: 'tnc:projectile/wind_tornado'
    referenced from: tnc:projectile/wind_tornado: java.io.FileNotFoundException: ...
```

### 8.1 根因：生成器把角度规则记错了

| | |
|---|---|
| **真规则** | `rotation.angle` **只能是这五个值**：`-45 / -22.5 / 0 / 22.5 / 45` —— 别的**直接抛异常** ✗ |
| **生成器当时以为** | 「22.5 的整数倍」✗ —— **错**：`90` 和 `135` **都是** 22.5 的整数倍，**照样被拒** ✗ |
| **本模型实际吐的** | 7 层漏斗 × `TWIST_DEG = 22.5` ⇒ `0 / 22.5 / 45 / **67.5** / **90** / **112.5** / **135**` ✗ |
| **后果** | **一个元素抛异常 ⇒ 整个模型不烘焙** ✗ ⇒ 引擎取到 missing model ⇒ **紫黑** ✓ |

**为什么风刃好的**：`windblade` 的旋转角**全是 0** ✓ —— 同一个渲染通道、同一个贴图目录、同样登记烘焙，
**唯一差别就是角度** ✓。这也解释了「紫黑」每次都只出现在龙卷风上 ✓。

### 8.2 §七 那份复盘**结论是错的**（保留，但以本节为准）

- §7.1 说「根因 ＝ `texture_size` ⇒ 模型根本没被烘焙」✗ —— **删掉它之后紫黑依旧** ✗，
  所以那不是这次的原因 ✓。旁证：整合包里那份带 `"texture_size": [64,64]` 的
  `kubejs/assets/tnc/models/projectile/thunder_ball.json` 是**烘焙成功**的 ✓
  （它在日志的 `Missing textures in model ...` 名单里，而**真失败**的 `tnc:block/gamble_table`
  **不在**那份名单里）⇒ `texture_size` **非标准、该删** ✓，但**不等于不能烘焙** ✗。
- §7.2 的退化 UV（两值）**是个真问题** ✓（会让整个面塌到一个像素），但它**不导致紫黑** ✗。
- §7.3 的闸门 D1b10 当时只查「`texture_size` + 四值 UV」✗ ⇒ **恰好漏掉了真正致命的那一项** ✗。
- **真正的教训**：这一节的检查全是**文件层面**的（文件在不在、字段干不干净、尺寸合不合法）✗ ——
  而「**能不能烘焙**」是**原版反序列化器**说了算 ✓。**"文件在" ≠ "能烘焙"，"字段干净" ≠ "能烘焙"** ✓。

### 8.3 修法：把扭转**拆成两半**，几何一模一样（已验证 ✓）

不能简单把 `TWIST_DEG` 压到 7.5（那会把作者要的扭转砍掉 ✗）。做法：

- **90° 的整数倍那部分** ⇒ **直接烤进方块的 `from/to` 坐标** ✓ ——
  绕竖直中轴转 90° 会把**轴对齐的方块的边对齐到另一个轴对齐方块** ✓（无损 ✓，
  7 层里 `67.5→-22.5`、`90→0`、`112.5→22.5`、`135→45` 各转 90°/180° 补回）；
- **剩下的余数**（一定落在 ±45 内）⇒ 写进 `rotation.angle` ✓；
- 两半**绕同一个轴心**，可交换 ⇒ **合成结果 = 原来的 yaw** ✓ ⇒ **形状完全不变** ✓。

**无损性是机器验过的** ✓（不是嘴说）：把 `HEAD` 版模型和重新生成的模型逐个元素求
「**坐标 ＋ 旋转后**」的 8 个角点集合，**32/32 元素完全相同** ✓（差异 0）。

`paint_preview()` 也跟着改了：预览图必须**补回余数旋转**才能画出真实形状 ✓
（否则预览会撒谎——它画的是烤进坐标之后、还没转回来的方块 ✗）。

### 8.4 补的闸门（这次真的堵住了）

1. **生成器** `check_rotations()` —— 角度不在那五个值里就 **`REFUSING:` 拒绝生成** ✗；
   头注释里那句错的「22.5 的整数倍」也**改成了真规则** ✓（免得下次再照着它写）；
2. **`tools/verify_mod_jar.ps1` 的 D1b10** 扩成三项：**旋转角 / `texture_size` / 四值 UV** ✓，
   `Ok` 文案也改成 `rotation angles legal, ...` ✓。

### 9.1 不是圆心旋转 ⇒ 渲染器**多补了一次** −0.5（实锤 ✓）

**现象**：龙卷风不是原地自转，而是**绕着身边一个小圈甩** ✗。

**根因**：两个渲染器都在缩放后补了 `translate(+0.5, +0.5, +0.5)`，而**引擎自己也补了一次**：

| | |
|---|---|
| **引擎** | `CustomModels.render` 里 `poseStack.translate(-0.5,-0.5,-0.5)` —— **反编译实例里那份 `spell_engine-0.15.12+1.20.1.jar` 核对过** ✓（`class_4587.method_22904(-0.5d,-0.5d,-0.5d)`）。作用：把"方块模型空间"（0..16 单位 ＝ 0..1 格、原点在角上）挪成**以原点为中心** ✓ |
| **我们的模型** | 包围盒 **x/z 以 (8,8) 单位为中心**（＝ 0.5 格）✓ ⇒ 引擎那一句**正好**把它对到实体中轴 ✓ |
| **我们又补的** | `+0.5` ⇒ **再偏 0.5 格** ✗ ⇒ 转起来就是"绕圈甩" ✗（x/z 各偏 0.5 ⇒ 斜角 0.71 格 ✓） |

> ⚠️ 那份**错误注释**（"引擎内部先 translate(−0.5…)…所以补 (+0.5,+0.5,+0.5) 正好"）**是错的** ✗ ——
> 它把"抵消"当成了"补偿"：引擎已经不欠我们了，再补就过量 ✓。这是**照抄**黑夜之手/环绕雷球那两份注释来的 ✗。

**改法**（`TNTornadoRenderer`）：

- **x/z 一个字都不补** ✓（交给引擎那句 −0.5）；
- **y 补 +0.5** ✓ —— 本模型底边在 `y=0`（漏斗站地上 ✓、不是居中 ✗），引擎的 −0.5 会把它**沉下半格** ✗；
- 合起来 `translate(0, +0.5, 0)` ✓ ⇒ 中轴对齐 ＋ 底边贴地 ✓。

**顺手修了同一类错的月牙渲染器**（`TNWindBladeRenderer`）：月牙的包围盒**以 (8,8,8) 单位为中心**（三个轴都居中 ✓）
⇒ 引擎那句 −0.5 **已经**把它对到实体原点了 ✓ ⇒ 它**一个字都不该补** ✗（原来补了 +0.5 ⇒ 画面偏出 0.87 格，
判定在中心、看着在偏旁 ✗）。

> 📌 **同一个坑还可能在别处**（本轮**没动**，只登记）：凡是"模型以 (8,8) 单位为中心 ＋ 渲染器补 (+0.5,+0.5,+0.5)"
> 的组合，都会偏 0.5 格。已知同类写法：`TNNightGripRenderer` / `TNThunderOrbRenderer` /
> `TNDarkFog`（黑雾那份模型是**故意**把底边放在 y=8 的 ✓，口径不一样 ⇒ 改之前要先核那一条链的实测效果 ✗）。
