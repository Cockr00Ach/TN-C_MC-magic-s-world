# 自制投射物模型 · 已验证可用的配方（2026-09-20 攻克）

> 这一条流水线是**实测打通**的（火球 `tnc:fireball` 已正常显示）。照抄即可，不要改顺序。

## 完整配方（6 步）

| # | 做什么 | 位置 / 内容 |
|---|---|---|
| ① | **模型文件** | `assets/tnc/models/projectile/<名字>.json`<br>原版 Java 方块模型；**不要 `texture_size`**；`rotation` 必须单轴 + 角度只能 `-45/-22.5/0/22.5/45`；**贴图引用写 `"0": "tnc:spell_projectile/<名字>"`** |
| ② | **贴图** | `assets/tnc/textures/spell_projectile/<名字>.png`（**目录必须是 `spell_projectile`** ✗ 不是 `projectile`）|
| ③ | **告知引擎** | `TNProjectileModels` 里 `CustomModels.registerModelIds(...)` 加上这个号（**反射调用**，因为我们是 Forge 模组而 SpellEngine 是 Fabric）|
| ④ | **强制烘焙** ★ | `TNModelBaking` 里 `ModelEvent.RegisterAdditional` 注册 `new ModelResourceLocation(id, "standalone")` —— **这一步最关键**，漏了它模型永远不会被烘焙 → 紫黑方块 ✗ |
| ⑤ | **法术引用** | 法术 JSON（必须在 **mod jar 的 `data/tnc/spells/`** 里）：`"model_id": "tnc:projectile/<名字>"` |
| ⑥ | **禁忌** | kubejs 里**不能有同名法术副本** ✗（数据包后加载会覆盖 jar 版本）|

## 排查"紫黑方块"的正确顺序（血泪教训）

1. **先读日志** ✗（我绕了几小时才做 ✓）：
   ```powershell
   Select-String -Path logs\latest.log -Pattern 'tnc:projectile' -Context 0,2
   ```
   - `Missing textures in model tnc:projectile/X: ...` → **模型被烘焙了 ✓ 但贴图引用错** ✗ → 检查 ② 的目录与 ① 的引用 ✓
   - **完全没有这行** → **模型没被烘焙** ✗ → 检查 ④ `RegisterAdditional` ✓
2. 再用二分法：把 `model_id` 换成一个**已知能显示**的号 ✓（本项目里是 `tnc:projectile/lightingball` ✓）→ 能显示就是**号/文件**的问题 ✓，不能就是**法术 JSON**的问题 ✓。

## 环境坑（都踩过）

- **打包 zip 必须用正斜杠条目名** ✗（Windows 默认反斜杠 → MC 完全读不了 → 资源包"启用却无效"）
- **`JAVA_HOME` 被 PCL 占用会让 gradle 静默不编译** ✗；`identical: True` 可能只是**两个旧文件互相比** → 必须**核对 jar 内容** ✓（已固定用 `D:\ModTest\.jdk17`）
- **不要改 Fabric 模组的 jar** ✗（Connector 重映射失败 → 启动崩溃）
- `sync.cmd` 是**双向**的 ✗：删了 kubejs 里的文件后不要再跑 sync ✓，否则游戏侧旧副本会被同步回仓库 → 再次覆盖 jar ✗
