# 特殊魔法（领域魔法）设计草案

> 依据：设计总纲 §12.F
> 「特殊魔法是不同属性所拥有的不同底层逻辑领域魔法，**无法升级**，为完成委托获取该属性特殊魔法路线，
> **获得路线即获得魔法**，属于规则魔法…并且**领域魔法等级只与亲和力有关**」

## 一、文档的要求拆成三条硬规则

| 规则 | 含义 | 与现有机制的关系 |
|---|---|---|
| **无法升级** | 没有 1→5 级，学会就是学会 | 和"链"完全不同 ✗ 不能塞进 `Chain` |
| **获得路线即获得** | 解锁靠"拿到路线"（委托/任务），不靠点数逐级买 | 类似现在的解锁，但**一次性** ✓ |
| **只与亲和力有关** | 强度不看等级、不看装备，**只看该元素亲和力** | 现在亲和力只用来**卡等级** ✗，不提供任何强度 ✗ —— 这是**新增能力** |

**结论**：特殊魔法不是"第五条链" ✗，而是一套**平行的小机制** ✓，需要新数据结构。

## 二、数据与界面怎么落

### 2.1 数据结构（建议）

```java
// SpellCatalog 里加一个平行列表，不进 chainsOf()
record Special(ResourceLocation id, Element element, String displayName, Element affinitySource) {}

static List<Special> specials();                 // 每个元素一条
static boolean knowsSpecial(MagicStoneData, Element);
```

`MagicStoneData` 加一个字段：`Set<Element> specials`（NBT 里存字符串集合 ✓ 向后兼容 ✓）。

**为什么不塞进 Chain**：自检断言"每条链 5 级" ✓ —— 特殊魔法只有 1 级 ✗，塞进去会**破坏那条断言** ✗。

### 2.2 亲和力 → 强度（核心）

三种做法，我推荐 **A**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 学会特殊魔法后，按亲和力给**该元素学派属性的永久加成**：`spell_power:<element>` = 亲和力 × 每点 X% | 用现有属性系统 ✓ 引擎自己会算 ✓；"只看亲和力"天然成立 ✓ |
| B | 特殊魔法是个自定义效果，Java 每 tick 维护 | 多一份状态要同步 ✗ 容易和别的效果打架 ✗ |
| C | 给特殊魔法做独立伤害公式 | 得绕过引擎的伤害管线 ✗ 工作量最大 ✗ |

**A 的细节**：
- 亲和力 0~6 → 加成 0~30%（每点 +5%）
- 通过 `AttributeModifier`（`MULTIPLY_BASE`）挂在 `spell_power:<element>` 上
- 亲和力变化时（`/tnc affinity set` ✓）要**重算修饰符** ✓ —— 这是最容易被漏掉的一步 ✗

### 2.3 获取方式

- 命令：`/tnc special grant <元素>`、`/tnc special list`（先做命令 ✓，委托系统还没有 ✗）
- 界面：魔法石界面每列下面加一行"领域魔法：未获得/已获得" ✓（点不动，只是展示 ✓）

## 三、建议的落地顺序（每一块都能独立编译+验收）

1. **数据层**：`MagicStoneData.specials` 字段 + NBT 读写 + `SpellCatalog.Special` 列表 + 自检断言
2. **命令层**：`/tnc special grant|revoke|list`
3. **亲和力加成**：学会后按亲和力挂 `spell_power` 修饰符（含"亲和力变了要重算"✗ 这个坑）
4. **界面展示**：每列底部一行状态
5. **法术本体**：每个元素 1 个 JSON（`AREA` 或 `CLOUD` 模板 ✓ 现在写起来很快 ✓）

## 四、需要你拍板的两点

1. **每点亲和力给多少加成**？（我建议 **每点 +5%，满 6 点 = +30%** ✓ 不夸张但明显 ✓）
2. **每个元素的领域魔法叫什么、什么效果**？文档只写了 S/M 的光暗领域（"拥有与其他冒险者特殊魔法组合的能力，组合之后获得特定环境 buff 和抗性"）✗ —— 七个元素各自的领域内容还没有 ✗。
