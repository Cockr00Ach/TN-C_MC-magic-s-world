## 一、★「释放黑雾游戏闪退」—— 根因是**用了不是粒子的粒子 id**（已修）

### 1.1 证据（游戏日志实锤，不是推测）

```
[20:25:11.418] [Server thread/WARN] [TN-C/fog/]: TN-C: gate ALLOW tnc:black_mist mana 125 / 20
[20:25:11.420] [Server thread/INFO] [TN-C/fog/]: TN-C: fog circle spell=tnc:black_mist r=5.0 life=320
[20:25:11.660] [Netty Local Client IO #0/ERROR] Encountered exception while handling in channel
                with name "spell_engine:particle_effects"
java.lang.ClassCastException: class net.unusual.block_factorys_bosses.init.BossesRiseParticleTypes$1
  cannot be cast to class net.minecraft.core.particles.ParticleOptions
    at net.spell_engine.particle.ParticleHelper.convertToInstructions(ParticleHelper.java:146)
    at net.spell_engine.client.ClientNetwork.lambda$initializeHandlers$3(ClientNetwork.java:25)
    at net.fabricmc.fabric.impl.networking.client.ClientPlayNetworkAddon.receive(...)
```

同一份日志里这类异常 **298 次**，全部是同一个类 ✓；**没有任何**别的粒子类出问题 ✓。

### 1.2 根因

黑雾五档第一版用了 `block_factorys_bosses:ink_fog` / `:fog_1`。这两个 id：

- 在**那个 mod 的资源里真的有** `assets/block_factorys_bosses/particles/ink_fog.json` ✓ 和贴图 ✓；
- **但它们不是 Minecraft 粒子** ✗ —— 那个 mod 把它们注册成了 **Bedrock 粒子**
  （`registerBedrockParticle(String)`）；
- ⇒ `BuiltInRegistries.PARTICLE_TYPE` 查不到 ⇒ Forge 返回它自己的对象 ⇒
  引擎照惯例 `(ParticleOptions)` 强转 ⇒ **ClassCastException**；
- ⇒ 而它抛在**客户端读 `spell_engine:particle_effects` 包**的时候 ✗ ⇒ netty 通道死掉
  ⇒ 游戏掉回主菜单（＝"闪退"）✗。

### 1.3 为什么我本地（服务端日志）看着只是 WARN

同一 tick 里 `ParticleHelper.play:121` 还打了 298 条
`Failed to play particle batch - class net.unusual.block_factorys_bosses...` ——
那是**本地**那条路（引擎自己 catch 了，所以只是刷屏）✓；
**网络包**那条路没人 catch ✗ ⇒ 只有客户端的收包线程会死 ✓。
**教训：服务端日志只是 WARN，不代表客户端没事。** ✗

### 1.4 修法

| 项 | 处理 |
|---|---|
| 黑雾五档的粒子 | 全部换成**逐个 javap 查过是真 `ParticleType`** 的 id ✓：`minecraft:squid_ink`（唯一的原版墨黑）＋ `minecraft:smoke`（体积）＋ `fromtheshadows:shadow`（压实的暗色汽）＋ `minecraft:soul` / `soul_fire_flame` ＋ `soulsweapons:black_flame` ＋ `block_factorys_bosses:soul_flip`（那个 mod 里**唯一**查过是 `SimpleParticleType` 的一个 ✓）|
| 献祭五档 | 同样清掉 `ink_fog`，改用 `fromtheshadows:shadow` ✓ |
| 生成器闸门 | `tools/gen_dark_fog_spells.py` 里加了 `FORBIDDEN_PARTICLES` 黑名单 ＋ 生成后**逐法术扫描**，命中就报错不写文件 ✓ |
| ★ 构建期闸门（新） | **`src/test/java/.../magic/SpellParticleSafetyTest.java`**：把 jar 与整合包两份法术 JSON 里出现的**每一个 `particle_id`** 收集起来，不在"已验证名单"里就**构建失败** ✗，并告诉你"先用 javap 确认它是 `ParticleType` 再登记"✓ |
| 文档 | 生成器头部写了 **PARTICLE SAFETY** 段落（含这次事故的完整因果）；`docs/previews/dark_fog_particle_candidates.png` 里那几个 ink_fog/fog_1/mist_cloud 从此只是**反面教材** ✗ |

> ★★ **新增铁律（第十三条）**：**「`assets/<ns>/particles/<id>.json` 存在」证明不了任何事** ✗
> —— 能不能当 `particle_id` 用，**只看那个 mod 有没有把它注册成 `ParticleType`**。
> 验证手法：`javap -p -classpath <mod jar> <它的粒子注册类>`，那一行必须是
> `RegistryObject<SimpleParticleType>`（或 `ParticleType<... extends ParticleOptions>`）✓。
> **只看资源文件 = 可能把客户端打崩** ✗（本次事故）。
> 项目里另一个同类坑（`TNAngelEntity.getBoundingBoxForCulling`）说明"这类静默差异必须离线钉住"✓。

### 1.5 顺手修掉的两条噪音/隐患

1. `TN-C: fog radius lookup failed (NPE: "power" is null)` 那条 WARN 是**误报** ✗：
   `combinedRadius(null)` 只在**真的有 `extra_radius`**（按法术强度放大半径）时才会去读参数，
   我们五档都没写 `extra_radius` ⇒ 传 null 合法 ✓。现在只在**真抛异常**时兜底 ＋ 警告 ✓
   （半径也会退化成 `FALLBACK_RADIUS`，施法不会崩 ✓）。
   副作用：t1 黑雾的边界圈半径从兜底的 5.0 变成**真实的 4.5** ✓。
2. 雾实体里"清理多余法阵"原来**在实体遍历的调用栈里 `discard()`** ✗ ——
   和 `ConcurrentModificationException` 的经典模式一模一样。
   虽然这次日志里那条 CME 是 Forge 关服时的已知噪音（`ObjectHolderRegistry`，与本模组无关 ✓），
   但这条隐患已经改成**下一 tick 再删** ✓（延迟一帧，肉眼看不出）。

## 二、「释放完之后一直掉血」—— 燃血那条路有两个真问题（已修）

**现象**：以伤换伤链放完之后，血一直在掉、身上一直掉血粒子 ✗。

**先厘清"设计上就该掉血"的部分** ✓：这条链就是**拿血换暗属性强度**
（t1 不烧 / t2 1%每秒 / t3 2% / t4 3% / t5 血锁 1），效果时长 20~30 秒 —— 那是设计 ✓。
但代码里确实有两个真问题：

1. **掉血有时会"卡住不动"** ✗：原来用 `player.setHealth(health - drain)`，
   而它**绕开原版的受伤窗口**（`invulnerableTime`，10 tick）—— 在"刚被打过/刚烧过"的玩家身上
   会被原版静默丢掉 ⇒ 表现就是"有时掉、有时不掉" ✗。
   **已改为** `player.invulnerableTime = 0; player.hurt(damageSources().magic(), …)` ✓：
   ① 每秒那一下**一定**生效；② 走真正的伤害管线（扣血提示 / 屏幕红闪 / 死亡判定都是原版）✓；
   ③ 扣血前先夹住 ⇒ **永不致死**（保底 1 点）✓ —— 作者当初确立的规则一个字没变 ✓。
   **火系燃烧线同病同修** ✓（两条链共用同一条规则，不该有一边是坏的 ✗）。
2. **"掉血粒子"= 效果粒子的可见性** ✓：`show_particles: true` 的那几个效果会在身上持续撒粒子，
   时长就是效果时长（20~30 秒）—— 这是原版行为，但它让"还在烧"这件事看起来很烦 ✗。
   现在**每档的 HUD 上都直接写明**（中英双语已加 lang）：
   `effect.tnc.blood_mark 血之烙印 / blood_burn 燃血 / blood_sacrifice 献祭 / blood_possess 夺舍 / blood_god 我为神`
   ⇒ 玩家一眼能看出"现在烧的是第几档、还剩多久"✓。

> ⚠️ **如果作者的本意是"连粒子也不该在结束后还在"，那是另一件事** ✗
> —— 现状是"效果在时长内 → 一直掉血 ＋ 一直有粒子"（设计 ✓），
> 效果一到期两者**同时停** ✓。要不要把时长砍短、或者把粒子关掉，
> 都是一行改动（JSON 的 `duration` / `show_particles`）✓ —— 等作者确认"到底哪一种"。

## 三、黑夜之手体积：t2 ×2 / t3 ×5 / t4 ×10 / t5 ×20（已实装）

**换算规则（体积 → `scale`）**：`scale` 乘的是**每一维** ⇒ 体积按**立方**涨 ✓

```
new_scale = base_scale * volume_multiplier ** (1/3)
```

模型（`tnc:projectile/dark_hand`）五档**共用同一只手** ✓，基准取 t1 的 `0.85`：

| 档 | 法术 | 体积倍率 | `scale`（旧→新）| 长度（模型 1.88 格 × scale）|
|---|---|---|---|---|
| t1 | `night_hand` 黑夜之手 | ×1（不变）| 0.85 → **0.85** | 1.60 格 |
| t2 | `night_raid` 黑夜之袭 | **×2** | 1.05 → **1.07** | 2.01 格 |
| t3 | `night_embrace` 黑夜之拥 | **×5** | 1.30 → **1.45** | 2.73 格 |
| t4 | `black_ruin` 黑之破灭 | **×10** | 1.55 → **1.83** | 3.44 格 |
| t5 | `slay_light` 戮光 | **×20** | 1.80 → **2.31** | 4.34 格 |

- 生成器：**`tools/gen_dark_hand_scales.py`** ✓（改 `VOLUMES` 字典即可重来）。
- ⚠️ **这五个法术住在 mod jar 里**（不是 kubejs）—— 因为 `6b29d3af` 把"用了模型的法术"
  统一搬进 jar 了（kubejs 同名副本会**静默盖掉** jar 的定义 ✗）⇒ 加了一行断言拦住写错目录 ✓。
- ⚠️ **如果作者本意是"边长 ×2/×5/×10/×20"而不是体积**：那 `scale` 就该是
  `0.85 × 倍率`（t5 = 17 ⇒ 约 32 格长，比两个区块还大 ✗）。**改一个字典就行** ✓，等作者拍。
