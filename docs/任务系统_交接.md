### 4.2 ★ 代码层：把作者任务书从**字节码**删掉（`tools/ClearAuthorQuestbook.java`）

**这一刀切在哪**：

```

任务书本体全在 registerNativeChapters()        → 注册章节 + 139 处 registerQuest
⇒ 把 registerNativeChapters() 的方法体清成单条 RETURN
⇒ NPC / 对话 / 实体代码**不受影响** ✓
```

| 项 | 值 |
|---|---|
| 目标类 | `com/example/ysjxmodel/quest/YsjxQuestIntegration` |
| 目标方法 | `registerNativeChapters()V` |
| 实测产物 | `build/tmp/surgery/ysjxmodel-cleared.jar` |
| 原始备份 | `build/backup/ysjxmodel-1.0.0.jar.orig`（**797,583 B** / SHA `6A2CB87F…`）|
| 已装机 | 实例 `mods\ysjxmodel-1.0.0.jar` = **797,293 B** / SHA `18969EF6…` / 2026-09-27 22:19 ✓ |

> ⚠️ **踩过的坑（写在这里省得重踩）**：第一版只拦了 `visitEnd`（以为不转发就丢掉了整段体），

> ⚠️ **这是"改第三方 jar"** —— 与项目铁律 ④「不要改 Fabric 模组 jar」**不冲突**：

## 六、★★ 五条硬知识（都是实测出来的，别再踩）

### 6.1 ★★★ 任务书**只显示三种任务**，且 `start_triggers` 会**反向锁死** `startQuest`

**第一条：任务书界面只显示三种任务** —— "定义里有"≠"界面里看得到" ✗

```
· 已接取进行中的   activeEntries
· 有奖励可领的     claimableRewardEntries
· 刷新池里的       refreshedEntries
```

没被接取的任务**永远不出现**。这就是"任务书里看不到我们任务"的根因
（服务端解析 ✓、下发 ✓，三层诊断 mixin 已确认）。

**第二条（2026-09-28 实锤，反直觉）**：任务一旦声明了 `start_triggers`，
**就不能再用 `startQuest()` 直接接取** ✗ —— `canPlayerTake` 会检查
"有 start_triggers **且** 还没进 `triggeredQuests`" → 直接 `return false`。

实测证据（`logs/latest.log`，存档内玩家当时**没有** `minecraft:story/root` 成就）：

```
22:51:30  TN-C quest-dump: [我们的] tnc:main/self_talk = {... "start_triggers":[{...story/root}]}
22:51:54  Cockr0Ach[local:...] logged in with entity id 2313
22:51:55  [TN-C quest] startQuest 返回 false：tnc:main/self_talk     ← 被上面那条规则挡住
```

**两条解法（二选一，别混着用）**：
1. **声明 `start_triggers` ⇒ 就交给触发器** —— 玩家满足条件时引擎自己会接取；
2. **要自己用脚本接取 ⇒ 就不同时声明 `start_triggers`** ✓（**本任务采用的**）。

> ★ **`self_talk` 的最终修法**：删掉 `start_triggers` 段（并顺手删掉变通留下的
> `refresh_pool: "daily"`）⇒ 脚本 `startQuest` 直接成功 ✓。
> 现在它的门是：等级 ≥ `min_player_level`(0) ✓、无 `required_completed` ✓、
> 无被别的任务 publish 的前置 ✓、无 `blocked_by_active` ✓。

> 🔧 **复现工具**：`tools/dump-whisperingquests-api.ps1`（纯 ASCII ✓）
> —— 把 `whisperingquests-*.jar` 里 API/数据/门禁三个类反编译出来，
> 并在末尾打印 `canPlayerTake` 的**五条 false 条件**。
> 这个 mod 闭源无 javadoc，**门禁规则只在字节码里** ⇒ 改任务前先跑它 ✓。


### 6.2 ★★ FTB 会重写所有 id（如果哪天又要用 FTB，先读这条）

实测（2026-09-23 21:16 写、进一次游戏后被改）：

| 对象 | 我写的 | 进游戏后 |
|---|---|---|

### 6.3 KubeJS 的 `const`/`let` 坑 —— 脚本里别声明局部变量

`tnc_quest_start.js` 里**不要**写 `const` / `let` 声明局部变量 ✗：
实测抛 `InternalError: TypeError: redeclaration of var xxx`

**改用**：接收函数参数 ＋ 顶层 `var`（KubeJS 脚本重载会重复求值，顶层 `var` 可重入）✓。

| 命令 | 行为 |

### 6.5 ★★★ 我们的对话**不会**自动完成 WhisperingQuests 的 `dialogue` 目标（2026-09-29 实锤）

**症状**：跟 Self 对完话，任务还是没完成。

**根因**：WhisperingQuests 自带的 `QuestDialogueHandler` 只在两种情况推进"对话类"目标：
1. 被右键的实体是原版 **`Villager`**，或
2. 那个实体走 **`p1nero_dl`** 对话库（`ServerNpcEntityInteractEvent`）。

TN-C 的剧情 NPC **两条都不占** ✗ —— 自研实体 ＋ 自研 `DialogueNetwork`。
⇒ **它的完成回调根本不经过我们**，必须我们自己往回推。

**解法：剧本里加 `@quest` 指令**（本章新增的桥）

```
data/tnc/dialogues/<npc>_first.txt
    @id    tnc:self_first
    @quest tnc:main/self_talk      ← 这段演完 = 完成这个任务
    ...
```

| 环节 | 在哪 |
|---|---|
| 解析 `@quest` | `dialogue/DialogueLoader`（★ 必须排在"说话人\|台词"判断**之前**，否则没有竖线会被当格式错误 ✗）|
| 存字段 | `DialogueScript.quest`（**只在服务端用，不走网络** ✗ —— 客户端不需要知道这段戏完成哪个任务）|
| 触发时机 | `DialoguePackets.DialogueDone::handle` —— 放在 `markSeen` 之后、`playNext` 之前。**必须等"真的播完"**：玩家中途关掉对话不算完成 ✓ |
| 真正调用 | `dialogue/compat/WhisperingQuestBridge` → `QuestManager.completeDialogueObjective(player, questId)` |

**为什么桥用反射而不是 compileOnly 依赖**：用真依赖要搬 jar 进 `libs/`、改 `build.gradle`
的 `flatDir`/`fg.deobf`、还要每个人重跑 `fetch-libs.ps1` —— 为调**一个方法**代价太大。
反射方案**不改构建、不加依赖、任何人 clone 下来直接能编译** ✓。
（前提已核实：`whisperingquests-3.2.jar` **没被混淆**，`completeDialogueObjective`
就是真实方法名，所以反射签名稳定 ✓。）

**为什么不崩**：照 `npc/compat/MaidNpcSupport` 的写法，**全 mod 只有 `WhisperingQuestBridge`
提到 WhisperingQuests**；`available()` 只用 `ModList`，不碰对方任何类型 ✓。
没装该 mod 时降级为"对话照常播、任务不推进" ＋ 一条 WARN，**不会崩** ✓。

**验收**：`tools/verify_mod_jar.ps1` 新增闸门 —— **每个 `@quest` 必须指向真实存在的任务 JSON** ✗
（写错 id 时对话照样播、任务永远不完成，正是这次的坑）。当前输出：
`[ok] every dialogue @quest names a real quest (1 reference(s))`

**看日志验收**：
```

TN-C dialogue: finished quest objective via dialogue -> tnc:main/self_talk
```
第二行没出现、而第一行出现了 ⇒ 任务没接取或目标已完成（INFO，不是错误）。

### 8.4 位置怎么定（锚点机制，换存档自动跟岛走）

- 登记存 `<存档>/data/tnc_npc_placements.dat`，内容是 **`{锚点, dx, dy, dz}`**，不是世界坐标。
- 锚点来自天空岛：`CENTER` / `ARRIVAL` / `ORIGIN` / `GROUND_PORTAL`。
- **新存档自动采用默认登记**；**改完默认值要把 `VERSION` +1** ✗（不改老存档不补位）。
- 命令：
  ```
  /tnc npc here <id>          站在想要的位置登记（自动选最近的锚点）
  /tnc npc status             诊断：登记应然坐标 + 实体实际坐标/距离/Y差
  /tnc npc list | respawn | purge <id|all> | remove
  /tnc npc place <id> <锚点> <dx> <dy> <dz>     （锚点写 ABSOLUTE 则用世界坐标）
  ```

**踩过的坑（都修了，别再犯）**：
1. **贴地逻辑覆盖用户指定的 Y** —— 现在只做**最小必要修正**：站得住就原样用 ✓。
2. **跨模块取数据绕 NBT 会静默失败** ✗ —— 现在走天空岛开的公开访问器 `anchorPos` ✓。
3. **改了默认值，老存档不会更新** —— 现在存 `DefaultsVersion`，落后就刷新 ✓。
4. ★★ **"区块加载了"不等于"放得进实体"** —— 见 §8.5。

### 8.5 ★★ 为什么"日志说放了"却不等于"人真的在"

**症状**：日志里 `self` 每 5 秒被 `restored` 一次，**连着 18 次**；而 `remove()` 那条警告一次都没打。

**真因**：那段时间玩家离这块区块 **750 格**，区块不在**实体刻（entity ticking）**范围内 ——
放进去了也立刻被丢掉，下次复查又看不见，于是无限重刷。

**修法（两道，缺一不可）**：
1. `ensureOne()` 动手前先问 `ServerLevel.isPositionEntityTicking(pos)`
   （＝区块已加载 **且** 在某个玩家的 simulation distance 内），不在就**安静跳过** ✓。
2. 轮询 **5 秒 → 1 秒**，并补 `PlayerLoggedInEvent` / `PlayerChangedDimensionEvent` 两个补位时机。
3. 放完**立刻回查**（`findNear(..., 4.0D)`）—— 这是唯一可信的成功判据 ✓。

> **一句话**：**永远不要用"我调了 addFreshEntity"当作"实体存在"的证据** ✗ —— 回查一次。

### 8.7 实机验收：看两行日志就够

```
TN-C dialogue self-check: 5/5 script(s) ok -> cava_first(19行,gold), huai_first(9行,gold),
    self_first(21行,gold), zhuangquerang_first(14行,blue), zhuangquerang_second(28行,blue)
```

**一条不是 bug 的现象**：NPC 突然 `removed! reason=DISCARDED`，

⇒ 遇到同类 `DISCARDED` **先看前后 10 秒有没有别的模组的传送/清理日志**，别急着改 NPC 代码 ✓。
