## 二、★ 关键技术决定：几何为什么全部代码自绘

### 2.1 原版方块模型这条路走不通（三条硬理由，都有实证）

| # | 限制 | 实证 |
|---|---|---|
| 1 | 顶点必须在 **−16..32**（≈2 格） | `docs/启动卡顿排查-20261010.md` §四：`block/gamble_table.json` extents `0.0 .. 64.0` ⇒ 客户端日志 `Failed to load model` ⇒ **那张 4×2 赌博桌在游戏里从来没显示过** ✗ |
| 2 | 资源包会遮住 `tnc:models/**` | 同一条日志：`FileNotFoundException: tnc:models/block/...`（`options.txt` 里 `resources/TN-C` 排在模组资源之后 ✗） |
| 3 | element **只能绕单轴转固定角度** | `light/client/TNDragonModel` 头注释：41 根骨骼每根都是多轴 ⇒ 只能把骨骼链压进顶点 |

⇒ 滚轮/转盘要**逐帧任意角度** ✗、机器有 **2 格宽** ✗ ⇒ 只能自绘 ✓。

### 2.2 走的是工程里**已经验证过**的那条路

参照 `light/client/TNDragonModel.java` ＋ `TNDragonRenderer.java`：

- **自己发顶点**（`casino/client/TNCasinoGeometry`）✓，一次都不碰资源包 ✓；
- 旋转/位移就是 `PoseStack.mulPose(Axis.YP.rotationDegrees(...))` ✓ ⇒ 每帧任意角度 ✓。

### 2.3 纯色几何的"白图"坑（★ 这个坑很隐蔽，别踩第二次）

自绘也必须给管线**绑一张贴图** ✗，而我们要的是"顶点颜色是什么就画什么" ✓。做法：

1. 用原版自带的**纯白** `minecraft:textures/misc/white.png` ✓
   （已核 1.20.1 客户端 jar：**4×4 / colortype 2 / 像素 (0,0) = `[255,255,255,255]`** ✓）；
2. 发顶点时把 `uv` 显式写成 **`(0,0)`** ✓ ⇒ 所有顶点都采那一个像素 ✓；
3. 于是输出颜色**正好等于**顶点颜色 ✓ —— 不需要 UV 图集、不可能采错格子 ✓。

> ⚠️ **更正一条早先写错的笔记** ✗：本文件初版写着"原版**没有** `textures/misc/white.png`" ✓
> —— **这是错的** ✓。当时列 `textures/misc/` 目录时漏看了它 ✓。
> 实际存在 ✓（同目录另有 `missingno` / `pumpkinblur` / `vignette` / `forcefield` / `shadow` 等 ✓）。

> ⚠️★ **再更正一条（2026-10-08，这条更贵）** ✗：本文件初版第 2 步写的是
> "**一个 `uv` 都不写** ⇒ 原版默认取 `(0,0)`" ✓ —— **这也是错的** ✓，
> 而且直接导致**一放机器就崩游戏** ✗。详见下节 §2.4 ✓。

#### ⚠️★ 2026-10-08 踩的大坑：**在渲染路径里注册贴图 ⇒ 游戏卡死** ✗✗

**症状**（作者原话）：「赌博桌老虎机什么的都没有成功导入游戏，
**是紫黑方块并且放出来游戏直接卡死**」✓。

**真因分两层**，两层都是我自己写错的 ✗：

| # | 问题 | 证据 |
|---|---|---|
| 1 | **贴图 id 用了 `tnc:dynamic/casino_white.png`**，而且注册动作写在**渲染的时候**（`white()` 里判 `getTexture(...) == null` 就注册 ✓） | `logs/debug.log`：`Failed to load texture: tnc:dynamic/casino_white.png` ＋ `at ...TNCasinoGeometry.registerWhite(TNCasinoGeometry.java:164)` ✓ |
| 2 | 那条链被 **azurelibarmor 的 `AnimatableTexture` mixin** 包了一层（它 hook 了 `TextureManager.register` ✓）⇒ 解析不到就**抛异常**，于是**每帧都抛** | 栈里 `mod.azure.azurelibarmor...AnimatableTexture` 插在 `TextureManager` 与我的 `registerWhite` 之间 ✓ |

⇒ 放下机器的一瞬间开始**每帧刷异常** ⇒ 游戏卡死 ✓；而"紫黑方块"就是
**贴图没绑上**的必然结果 ✓（管线只能画 missing texture ✓）。

**两条教训**：

1. **绝不在渲染路径里注册/改状态** ✗ —— 渲染只该读 ✓。
   要么在 `FMLClientSetupEvent` 里注册一次 ✓，要么（更好）**用一张本来就存在的图** ✓；
2. **别凭印象断言"原版没有这个文件"** ✗ —— 去 jar 里查 ✓（`zipfile.namelist()` 一行的事 ✓）。

**修法**：整块删掉 `registerWhite`，`white()` 改成**纯查表、零副作用** ✓，
直接用原版那张纯白 ✓。顺带把 `whiteRegistered` 这个可变静态字段也删了 ✓。

> 📌 同一个教训在 `TNDragonModel` 那边**没有**踩到，是因为它把注册放在
> **首次取用时**、而且用的是**自己内嵌**的贴图 ✓（一定解析得到 ✓）——
> 我照抄了"内嵌"的形，却漏了"一定解析得到"这个前提 ✗。

### 2.4 ⚠️★ 2026-10-08 实机崩：**漏发 `uv` ⇒ 一放下机器就崩游戏** ✗✗

**症状**：上一节的"卡死"修好之后，作者进世界、放下老虎机 ⇒ **客户端直接崩** ✗
（不是卡顿、不是紫黑，是崩 ✓）：

```
crash-2026-10-08_20.47.58-client.txt
Description: Rendering Block Entity
java.lang.IllegalStateException: Not filled all elements of the vertex
  at com.mojang.blaze3d.vertex.BufferBuilder.endVertex(BufferBuilder.java:264)
  at com.tnc.tnc.casino.client.TNCasinoGeometry.box(TNCasinoGeometry.java:94)
  at com.tnc.tnc.casino.client.TNSlotMachineRenderer.render(TNSlotMachineRenderer.java:164)
```

**真因**（一句话）：**赌场几何发的顶点少了一个元素** ✗ ——
三个渲染器都绑 `RenderType.entityCutoutNoCull` ✓，
⇒ 顶点格式是**实体那套**（`position + color + uv0 + overlay + uv2 + normal` ＋ padding ✓），
而 `box()` 只发了 `position / color / overlayCoords / uv2 / normal` ✓ —— **漏的就是 `uv0`** ✗。

**为什么"少发一个元素"不报错、只在最后炸一次** ✗（这条是本专题最值钱的认知 ✓）：

| 步骤 | `BufferBuilder` 实际行为 |
|---|---|
| 内部游标 | 有一个"**下一个该填哪个元素**"的游标 ✓（`elementsToFill` ✓） |
| 每次 `color/uv/overlayCoords/uv2/normal` | **先比对自己是不是"当前该填的那个"** ✗ —— 不是就<b>静默 `return`</b> ✓（**不抛、不提示、不写日志** ✗） |
| `endVertex()` | 游标没走完 ⇒ 抛 `IllegalStateException: Not filled all elements of the vertex` ✗ |

⇒ 所以"少发一个元素"和"顺序写错"**都是同一种崩** ✓，
而且**编译期、`verify_mod_jar.ps1` 全都查不出来** ✗（它不是资源问题，是顶点数据问题 ✓）。

**为什么全仓只有这一处踩到**（不是运气 ✓）：
本类是全仓**唯一**把 `POSITION_COLOR` 那套顶点喂给**实体格式**缓冲的地方 ✗。
其余自绘要么走 `POSITION_COLOR` 缓冲（`WaterRenderTypes.GEOMETRY` / `RenderType.lightning()` ⇒
`WaterGeometry.vertex` 与 `PortalRitualRenderer.vertex` 同样不发 uv ✓，
但它们的格式里**压根没有 uv 这个元素** ⇒ 合法 ✓），
要么走实体格式但**本来就都发了 `.uv(...)`** ✓
（`TNDragonModel` / `TNMagicCircleRenderer` / `TNLightningStrikeRenderer` / `TNFireBoltRenderer` /
`TNLightBeamRenderer` / `TNLightWingsModel` ✓）。

> ★ **铁律**：**换渲染类型（`RenderType`）＝ 换顶点格式** ✗ ——
> 顶点那几个元素**一个都不能省** ✓，而且**顺序也不能换** ✓。
> 自绘之前先问自己："这个 `RenderType` 的顶点格式里到底有几个元素？" ✓

**修法**：`box()` 里补一行 `.uv(0.0F, 0.0F)` ✓（常量 `UV_ZERO` ✓，采那张纯白的 (0,0) ✓）。
一个字符的事，但**它崩过一整局游戏** ✗。

**防回归（★ 这次新加的，别删 ✗）**：
`src/test/java/com/tnc/tnc/casino/client/CasinoGeometryVertexFormatTest.java` ✓ ——
一个**离线复刻 `BufferBuilder` 校验行为**的假 `VertexConsumer` ✓：

- **不解析源码文本** ✗，而是**真把 `box()` / `boxRotated()` 跑一遍** ✓；
- 期望的元素序列**不写死** ✓ —— 直接读 `DefaultVertexFormat.NEW_ENTITY` 的 `getElements()` ✓
  （实体渲染类型用的就是它 ✓），再逐个翻译成"该调哪个方法" ✓；
- 假缓冲**逐字复刻**上面那两条行为（顺序不对=静默丢弃 ✓、发不满=抛同一句异常 ✓）✓；
- 还带**两条反证** ✓（故意漏 `uv` ✓ / 故意把 `overlay` 抢到 `uv` 前面 ✓，
  两条都必须抛 ✓）—— 没有反证的话，"绿"说明不了闸门是真的 ✗。

⇒ 以后谁再动赌场几何、或者换掉渲染类型，`gradlew test` 立刻红 ✓，不必等作者崩一次 ✗。

> 📌 **实测细节（省得以后有人重新踩）** ✓：本仓实体顶点格式读出来是

## 三、★ 第二关键决定：动画在客户端，结果在服务端

```
服务端（权威 ✗）                     客户端（只负责好看 ✓）
─────────────────────               ─────────────────────────
右键 → 收 1 枚实体铜币              getUpdateTag() 收到：
     → 抽一次随机数                    Phase / Result[3] / StartedAt
     → 写进 Result[3]               每帧自己算角度：
     → 广播 getUpdateTag()             elapsed = 本机 gameTime + partialTick − StartedAt
     → N tick 后 settle() ⇒           ⇒ 亚 tick 丝滑 ✓
        算赔付、暂存 owed
```

- **每 tick 零网络包** ✓（只在状态跳变的少数几个 tick 才发 ✓）；
- 客户端**连随机数都碰不到** ✓ —— 这是这类功能唯一安全的做法 ✗
  （客户端定输赢的话，改个包就能必赢 ✓）。

**为什么两边的时间轴能对齐**：`StartedAt` 是**服务端**游戏时间 ✗，
而客户端**自己也有**游戏时间（`ClientLevel.getGameTime()`，由原版 `ClientboundSetTimePacket`
持续同步 ✓），两者同一条轴 ✓ ⇒ 相减就是"已经转了多久" ✓。

### 3.1 ⚠️ 踩过的坑：`sync()` 两支都必须发包

```
spinning 真的变了  ⇒ setBlock 会广播新状态，但**方块实体数据不会跟着发** ✗ ⇒ 必须补一发
spinning 没变      ⇒ （"出结果 → 复位"这两步都是 false ✗）客户端不重读 update tag
                      ⇒ 结果灯会**一直亮着不灭** ✗
```

⇒ 现在的 `TNMachineEntity.sync()` **无条件**再补一次 `level.sendBlockUpdated(...)` ✓。

### 5.1 ⚠️ 注册顺序：方块 → 方块实体类型 → 物品

`BlockEntityType.Builder.of(...)` 必须拿到**已经建好的方块实例** ✗，
而方块是在 `BLOCK` 事件里才 new 出来的 ✓。反过来的话传进去是**空数组**
⇒ 方块实体类型不认识任何方块 ⇒ 机器**不动、右键没反应，且一条错误都不报** ✗。
`RegisterEvent` 对同一注册表按挂载顺序触发 ✓，所以先后靠 `TNCasinoRegistry` 里的**书写顺序**保证 ✓。

### 5.2 ⚠️ 懒加载：`TNCasinoRegistry` 必须在 `TNMod` 里被强制加载

`@Mod.EventBusSubscriber` **只在类被加载后**才生效 ✗ —— 没有任何代码"提到"那个类时，
它根本不会被扫到 ⇒ 方块/物品/方块实体**静默不存在** ✓（本工程在 `TNScrolls` 上踩过同一个坑 ✓）。
所以 `TNMod` 构造函数里有一句 `Class.forName("com.tnc.tnc.casino.machine.TNCasinoRegistry")` ✓。

### 5.3 ⚠️ 每台机器一个自己的方块实体类型

不是共用一个 ✗ —— 方块实体类型决定反序列化时造哪个类 ✓，
共用会导致转盘桌读出存档后**变成老虎机** ✓。

### 5.4 ⚠️ `.java` 文件不能带 UTF-8 BOM

本机 PowerShell 5.1 的 `Set-Content -Encoding UTF8` **会写 BOM** ✗，
javac 直接报 `非法字符: '\ufeff'` ⇒ 编译失败 ✓。
用仓库里的 `write` 工具写文件（无 BOM ✓），**别用 shell 重定向** ✗。

### 8.1 ⚠️★ 一个很坑的失败模式：**被打断的构建会留下 0 字节的 Forge jar**

**症状**：连所有 `import net.minecraftforge.*` / `org.joml.*` 都报"程序包不存在" ✓，
外加一行：

```
java.io.EOFException: Unexpected end of ZLIB input stream
```

**看起来像**：代码写错了、依赖没了、缓存坏了 ✓ —— **都不是** ✗。

**真因**：构建过程中被强杀（例如我自己 `Remove-Item build` 撞上还在跑的 Gradle ✓），
`build/fg_cache/.../forge-1.20.1-47.4.22_mapped_official_1.20.1.jar` 会留下一个
**0 字节的占位文件** ✓。之后每次编译都读这个空 jar ⇒ 所有 Forge/JOML 类都找不到 ✓
⇒ 错误信息把所有 `import` 都说成"程序包不存在" ✓，**极其误导** ✗。

**查法**（一条命令，比读日志快 ✓）：

```powershell
Get-ChildItem build,.gradle-home\caches\forge_gradle -Recurse -File -Filter *.jar |
  Where-Object { $_.Length -lt 4096 } |
  ForEach-Object { "{0,8} bytes  {1}" -f $_.Length, $_.FullName }
```

**判据**：
- **0 字节**（或几百字节但本该是几十 MB）⇒ **垃圾，删掉整个 `build/` 重来** ✓；
- ⚠️ **`*-inject_src.jar` 只有 604 字节是正常的** ✗ —— 它本来就小 ✓，别当成损坏删了 ✓。

**预防**：不要在 Gradle 还在跑的时候删 `build/` ✓
（`[exit code: 1]` + `The directory is not empty` / `being used by another process`
就是这个信号 ✓）；等 java 进程退干净再删 ✓。
